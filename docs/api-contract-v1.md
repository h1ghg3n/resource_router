# Jetson Resource Router API Contract v1

Status: Frozen for v1 implementation
Frozen on: 2026-08-13
Base path: `/v1`
Media type: `application/json`

The v1 contract is frozen. Changes within `/v1` are limited to correcting a
contradiction, safety defect, or security defect without broadening product
scope. New capabilities or incompatible semantics require a later contract.

## 1. Purpose and boundary

The Resource Router is a cooperative, single-node admission controller for
Jetson Orin workloads. It atomically decides whether declared resource demand
may be admitted now and records successful decisions as leases.

The Router does not start, stop, suspend, or kill workloads. It does not enforce
Linux memory limits, CPU quotas, CPU affinity, or GPU quotas.

```text
ResourceClaim expresses declared committed demand for admission accounting.
It does not enforce OS-level resource limits.
```

Clients must declare conservative peak demand. A client must release a lease or
active reservation only after the associated resource use has stopped.

The v1 API has these deliberate constraints:

- one Jetson Orin node;
- one unified memory budget, not separate CPU RAM and VRAM pools;
- all-or-nothing grants; no partial resource grants;
- exactly two evaluated resource-acquisition outcomes: `GRANTED` and `BUSY`;
- no pending acquisition, queue, fairness, priority, or automatic drain intent;
- immediate EXCLUSIVE acquisition never drains existing leases;
- only a previously accepted EXCLUSIVE reservation may cause `DRAINING`;
- `retry_after_ms` is advice, not a promise of future availability.

Protocol, validation, and service-availability errors are not resource-
acquisition outcomes. In particular, `503 Service Unavailable` is not `BUSY`.
These failures use the error response described in section 5.

## 2. General conventions

### 2.1 Identifiers

- `request_id` and `lease_id` are UUID strings.
- `request_id` is generated by the client and identifies one logical acquire
  operation for its entire lifetime.
- `reservation_id` is a client-provided string matching
  `[A-Za-z0-9][A-Za-z0-9._:-]{0,127}`.
- Clients must not intentionally reuse request or reservation identifiers.

A request ID becomes bound at the Router only when acquisition is durably
GRANTED. BUSY, TELEMETRY_UNAVAILABLE, and ROUTER_RECOVERING do not bind or
reserve it. STORAGE_UNAVAILABLE can make the commit outcome unknown to the
client, so the client must retry the same request ID and normalized request
rather than assume either success or failure. The retry returns the persisted
grant if commit succeeded, or reevaluates admission if it did not.

A client retrying the same logical operation must retain both its request ID and
its normalized request. A changed claim is a new logical operation and must use
a new request ID. Because known non-granting attempts are not retained, the
Router does not guarantee detection of a changed request before that ID is first
GRANTED.

`client_id` is a trimmed string from 1 through 128 characters. It is a
diagnostic and ownership label, not an authenticated identity. Authentication
and network access control are deployment concerns outside this v1 contract.

### 2.2 Time

- All timestamps are RFC 3339 timestamps with an explicit UTC offset.
- Returned timestamps are authoritative.
- Lease expiry is exclusive: a lease is inactive when `now >= expires_at`.
- Reservation intervals use half-open bounds: `[start_at, end_at)`.

### 2.3 Units

- Fields ending in `_mb` represent MiB (`1 MiB = 1,048,576 bytes`). The `_mb`
  spelling is retained for API readability and compatibility.
- `cpu_cores` is a finite, non-negative number representing declared CPU demand
  in logical-core equivalents. It is not CPU affinity or a cgroup quota.
- Percentage values are numbers from `0` through `100`.

### 2.4 Forward compatibility

Clients must ignore response fields they do not understand. The Router rejects
unknown request fields in v1 to catch client mistakes early.

## 3. Core types

### 3.1 ResourceMode

```text
SHARED
EXCLUSIVE
```

`EXCLUSIVE` is node-wide in v1. It conflicts with every other active lease,
regardless of the requested resource vector.

### 3.2 ResourceVector

```json
{
  "memory_mb": 2048,
  "gpu": true,
  "cpu_cores": 2.0
}
```

| Field | Type | Constraint | Meaning |
|---|---:|---:|---|
| `memory_mb` | integer | `>= 0` | Declared commitment from Jetson unified memory |
| `gpu` | boolean | required | Whether local GPU execution is required |
| `cpu_cores` | number | finite, `>= 0` | Declared CPU demand for admission accounting |

At least one field must express non-zero demand: `memory_mb > 0`, `gpu = true`,
or `cpu_cores > 0`.

`memory_mb` includes the workload's expected unified-memory demand, including
memory used for GPU execution. `gpu` does not create a GPU-memory quota.

### 3.3 Lease

```json
{
  "lease_id": "01920000-0000-0000-0000-000000000001",
  "request_id": "018f5c30-0000-0000-0000-000000000001",
  "client_id": "flexraw",
  "mode": "SHARED",
  "resources": {
    "memory_mb": 2048,
    "gpu": true,
    "cpu_cores": 2.0
  },
  "granted_at": "2026-08-13T19:30:00+09:00",
  "expires_at": "2026-08-13T19:31:00+09:00",
  "status": "ACTIVE"
}
```

The only lease status returned as a lease representation is `ACTIVE`. Known
expired or released leases use `410 Gone` instead of returning a stale lease as
active.

## 4. Admission semantics

### 4.1 SHARED acquisition

A SHARED claim may be granted only when all of the following are true:

- the Router has fresh base telemetry and every metric required by the claim;
- no immediate EXCLUSIVE lease is active;
- no EXCLUSIVE reservation is draining or active;
- declared memory and CPU demand fit the lease ledger;
- observed memory headroom is sufficient;
- configured CPU and GPU pressure guardrails permit admission.

Multiple SHARED GPU claims may coexist. GPU scheduling is not fractional in v1.

### 4.2 Immediate EXCLUSIVE acquisition

An immediate EXCLUSIVE claim follows this rule:

```text
no active lease and no draining/active reservation
    -> evaluate capacity and pressure
    -> GRANTED if safe

one or more active leases
    -> BUSY / CONFLICTING_LEASES

draining or active EXCLUSIVE reservation
    -> BUSY / EXCLUSIVE_RESERVATION
```

A BUSY immediate EXCLUSIVE request does not change Router state, block new
SHARED claims, create a queue entry, or reserve future capacity.

### 4.3 Capacity accounting

Telemetry is observation; the lease ledger is commitment. Memory admission uses
both and must never treat telemetry as proof that committed capacity is free.

```text
allocatable_memory
= physical_memory - system_reserve

ledger_remaining
= allocatable_memory - sum(active lease commitments)

observed_headroom
= free_memory + conservatively_reclaimable_cache - emergency_reserve

effective_available
= min(ledger_remaining, observed_headroom)
```

CPU admission uses logical-core equivalents and a separate commitment ledger:

```text
maximum_allocatable_cpu
= max(total_logical_cpu_cores - system_cpu_reserve_cores, 0)

current_allocatable_cpu
= max(online_logical_cpu_cores - system_cpu_reserve_cores, 0)

cpu_ledger_remaining
= current_allocatable_cpu - sum(active lease cpu_cores commitments)
```

Observed CPU load is a pressure guardrail. It is not converted into free core
capacity because doing so can double-count work already represented by lease
commitments.

A claim larger than `allocatable_memory` or `maximum_allocatable_cpu` can never
fit this node and fails validation with `422 CLAIM_EXCEEDS_NODE_CAPACITY`. A
claim that fits the node maximum but not current ledger or observed headroom is
a temporary `409 BUSY` result.

Active reservations are also commitments during their active windows. The
Router does not add observed usage to lease commitments because that can
double-count workloads already visible in telemetry.

### 4.4 Telemetry completeness

Normalized telemetry represents an unavailable metric as JSON `null`; the
adapter must not invent a zero measurement. The minimum base snapshot required
for any new admission consists of a fresh observation time, total unified
memory, and free unified memory.

The following values may be unavailable independently:

- reclaimable cache, buffers, GPU-shared memory, and large-free-block memory;
- total and online CPU core counts and aggregate CPU load;
- GPU load;
- EMC load and maximum SoC temperature.

Missing reclaimable-cache telemetry contributes zero reclaimable memory.
Missing diagnostic-only values do not block admission. A claim with
`cpu_cores > 0` requires CPU capacity and load telemetry; a claim with
`gpu = true` requires GPU-load telemetry. If a metric required by that claim is
missing, acquisition fails with `503 TELEMETRY_UNAVAILABLE`, not BUSY.

## 5. Common error response

Validation, identifier-reuse, not-found, and terminal-lifecycle failures use:

```json
{
  "code": "REQUEST_ID_REUSED",
  "message": "request_id was already used with a different acquire request"
}
```

`message` is diagnostic text and must not be parsed by clients. Clients branch
on `code` and the HTTP status.

Common codes are:

| HTTP | Code | Meaning |
|---:|---|---|
| 404 | `LEASE_NOT_FOUND` | The lease identifier is unknown |
| 404 | `RESERVATION_NOT_FOUND` | The reservation identifier is unknown |
| 409 | `REQUEST_ID_REUSED` | The request ID is bound to a different acquire request |
| 409 | `RESERVATION_ID_REUSED` | The reservation ID is bound to different reservation data |
| 409 | `RESERVATION_CONFLICT` | The proposed reservation window conflicts with another reservation |
| 409 | `EXCLUSIVE_RESERVATION` | A reservation prevents the requested lease renewal |
| 410 | `LEASE_EXPIRED` | The known lease has expired |
| 410 | `LEASE_RELEASED` | The known lease was released |
| 410 | `RESERVATION_ENDED` | The known reservation has ended |
| 410 | `RESERVATION_CANCELLED` | The reservation was cancelled or released early |
| 422 | `CLAIM_EXCEEDS_NODE_CAPACITY` | The claim can never fit configured node capacity |
| 422 | `VALIDATION_ERROR` | The request does not satisfy the v1 schema or configured limits |
| 503 | `TELEMETRY_UNAVAILABLE` | Required telemetry is missing, invalid, or stale |
| 503 | `ROUTER_RECOVERING` | Persisted state has not been authoritatively reconciled |
| 503 | `STORAGE_UNAVAILABLE` | Authoritative state cannot be read or durably committed |

## 6. Lease API

### 6.1 Acquire a lease

```http
POST /v1/leases
```

Request:

```json
{
  "request_id": "018f5c30-0000-0000-0000-000000000001",
  "client_id": "flexraw",
  "mode": "SHARED",
  "resources": {
    "memory_mb": 2048,
    "gpu": true,
    "cpu_cores": 2.0
  },
  "ttl_seconds": 60
}
```

| Field | Type | Constraint |
|---|---:|---|
| `request_id` | UUID | required |
| `client_id` | string | 1..128 characters after trimming |
| `mode` | ResourceMode | required |
| `resources` | ResourceVector | required |
| `ttl_seconds` | integer | `1..max_lease_ttl_seconds` |

There are no `allow_pending` or `labels` fields in v1.

#### GRANTED

```http
200 OK
```

```json
{
  "status": "GRANTED",
  "lease": {
    "lease_id": "01920000-0000-0000-0000-000000000001",
    "expires_at": "2026-08-13T19:31:00+09:00"
  }
}
```

The grant is all-or-nothing. The committed resource vector is exactly the
requested vector. The lease and successful request record are persisted in the
same atomic operation before this response is sent.

#### BUSY

BUSY means the Router evaluated admission and denied it because of current
resource or ownership state.

```http
409 Conflict
```

```json
{
  "status": "BUSY",
  "reason": "INSUFFICIENT_MEMORY",
  "retry_after_ms": 3000
}
```

`retry_after_ms` is a minimum retry recommendation based on current policy. It
does not reserve capacity and does not guarantee that a later attempt succeeds.
There is no `available_after` field in v1.

| Reason | Meaning |
|---|---|
| `INSUFFICIENT_MEMORY` | Effective unified-memory capacity is temporarily insufficient |
| `GPU_PRESSURE` | Observed GPU pressure exceeds the configured guardrail |
| `CPU_PRESSURE` | Current CPU ledger or observed pressure prevents admission |
| `CONFLICTING_LEASES` | An immediate EXCLUSIVE claim conflicts with active leases |
| `EXCLUSIVE_ACTIVE` | An immediate EXCLUSIVE lease blocks this claim |
| `EXCLUSIVE_RESERVATION` | A reservation drain or active reservation blocks this claim |

A BUSY decision is side-effect free. In particular, it does not bind
`request_id` as a completed acquisition and may be reevaluated on retry.
Clients retrying the same logical acquisition must send the same request ID and
the same normalized request. A changed claim is a new logical operation and
must use a new request ID.

#### Admission unavailable

If the Router cannot evaluate admission safely, it does not return BUSY:

```http
503 Service Unavailable
Retry-After: 3
```

```json
{
  "code": "TELEMETRY_UNAVAILABLE",
  "message": "fresh GPU telemetry is unavailable",
  "retry_after_ms": 3000
}
```

The code is `TELEMETRY_UNAVAILABLE`, `ROUTER_RECOVERING`, or
`STORAGE_UNAVAILABLE`. The optional `retry_after_ms` remains advice and does
not guarantee future availability. When a retry delay is known, the Router also
sends the standard `Retry-After` header in whole seconds, rounded up from
`retry_after_ms`. TELEMETRY_UNAVAILABLE and ROUTER_RECOVERING do not create a
lease or bind `request_id`. After STORAGE_UNAVAILABLE, the outcome may be
unknown at the client; it must retry the same request ID and normalized body to
resolve the result safely.

#### Acquire idempotency

Successful acquisition binds `request_id` permanently in v1:

- same `request_id` and the same normalized request while the lease is active:
  return `200 GRANTED` with the same `lease_id` and the lease's current
  authoritative `expires_at` (which may have changed through renewal);
- same successfully bound `request_id` and a different normalized request:
  return
  `409 REQUEST_ID_REUSED`;
- same `request_id` after the original lease expired: return
  `410 LEASE_EXPIRED`;
- same `request_id` after the original lease was released: return
  `410 LEASE_RELEASED`;
- concurrent requests with the same `request_id`: create at most one lease;
- BUSY, TELEMETRY_UNAVAILABLE, and ROUTER_RECOVERING attempts are reevaluated
  and do not prevent a later GRANTED result using the same request ID and
  identical request;
- after STORAGE_UNAVAILABLE, retrying the same request ID and identical request
  either replays a grant that committed or reevaluates an attempt that did not.

The normalized idempotency comparison includes `client_id`, `mode`, the complete
resource vector, and `ttl_seconds`. Successful request records and terminal
tombstones are not recycled in v1.

### 6.2 Read a lease

```http
GET /v1/leases/{lease_id}
```

Active lease:

```http
200 OK
```

The response is the complete Lease representation from section 3.3.

Other responses:

- unknown lease: `404 LEASE_NOT_FOUND`;
- expired lease: `410 LEASE_EXPIRED`;
- released lease: `410 LEASE_RELEASED`.

Reading a lease does not renew it or create resource entitlement.

### 6.3 Renew a lease

```http
POST /v1/leases/{lease_id}/renew
```

Request:

```json
{
  "ttl_seconds": 60
}
```

`ttl_seconds` is measured from the time the Router processes the renewal. A
renewal never changes the lease's resource vector or mode.

Response:

```http
200 OK
```

```json
{
  "lease_id": "01920000-0000-0000-0000-000000000001",
  "status": "ACTIVE",
  "expires_at": "2026-08-13T19:32:00+09:00"
}
```

When an EXCLUSIVE reservation is approaching, the Router must cap the renewed
`expires_at` at the reservation's `lease_deadline`. The returned timestamp is
authoritative even when it grants less time than requested.

Renewing an ACTIVE lease does not require fresh telemetry because it neither
changes the resource vector nor introduces a new commitment. Keeping the lease
recorded is safer than allowing a still-running workload to disappear from the
ledger. Telemetry-related readiness failure therefore does not by itself block
renewal. Reservation deadlines and all persisted lifecycle rules still apply.

If persisted state has not been reconciled enough to identify the lease
authoritatively, renewal returns `503 ROUTER_RECOVERING`. If a reservation's
`lease_deadline` leaves no positive renewal interval, renewal returns
`409 EXCLUSIVE_RESERVATION`.

Other responses:

- unknown lease: `404 LEASE_NOT_FOUND`;
- expired lease: `410 LEASE_EXPIRED`;
- released lease: `410 LEASE_RELEASED`.

### 6.4 Release a lease

```http
DELETE /v1/leases/{lease_id}
```

```http
204 No Content
```

Release is idempotent. The Router returns `204` for active, already released,
expired, and unknown lease IDs. A successful acquire request tombstone remains
bound to its request ID after release.

Clients must stop the associated resource use before releasing the lease.

## 7. Reservation API

### 7.1 Reservation semantics

Reservations are fixed future EXCLUSIVE capacity windows. v1 does not support
SHARED reservations.

Each reservation derives two drain boundaries:

```text
drain_at       = start_at - drain_before_seconds
lease_deadline = start_at - reservation_safety_margin_seconds
```

`drain_at` closes new admission. `lease_deadline` is the latest permitted
expiry of a pre-existing lease, leaving the configured safety margin before
reservation activation.

An active reservation is itself the scheduled client's time-bounded resource
entitlement. The client does not call `POST /v1/leases` to activate or consume
the reservation. This avoids introducing a reservation-to-lease handoff token
or a hidden acquisition queue in v1.

Reservation phases are:

```text
SCHEDULED  now < drain_at
DRAINING   drain_at <= now, but the reservation is not yet safely active
ACTIVE     start_at <= now < end_at and activation is safe
ENDED      now >= end_at
```

Even when all leases exit early, a reservation remains `DRAINING` until
`start_at`. At or after `start_at`, activation requires fresh valid telemetry,
no conflicting managed lease, sufficient observed memory headroom, and passing
CPU/GPU pressure guardrails. If any blocker remains, the reservation stays
`DRAINING`; the Router does not report unsafe EXCLUSIVE ownership. The fixed
`end_at` is not shifted by delayed activation.

If activation never becomes safe before `end_at`, the reservation transitions
directly from DRAINING to ENDED. It grants no entitlement, is not extended, and
is not automatically rescheduled.

The reservation client must observe `status = ACTIVE` before starting resource
use and must stop no later than `end_at`. Acceptance of a future reservation
coordinates Router-managed demand, but cannot guarantee capacity against
unmanaged processes that bypass the Router.

### 7.2 Create a reservation

```http
POST /v1/reservations
```

Request:

```json
{
  "reservation_id": "night-heavy-20260813",
  "client_id": "scheduled-worker",
  "mode": "EXCLUSIVE",
  "resources": {
    "memory_mb": 7000,
    "gpu": true,
    "cpu_cores": 4.0
  },
  "start_at": "2026-08-13T23:00:00+09:00",
  "duration_seconds": 7200,
  "drain_before_seconds": 120
}
```

Validation rules:

- `mode` must be `EXCLUSIVE`;
- `start_at`, `duration_seconds`, and `drain_before_seconds` must produce a
  future non-empty window;
- `drain_at = start_at - drain_before_seconds` must be in the future when the
  reservation is first created;
- `drain_before_seconds` must be at least
  `max_lease_ttl_seconds + reservation_safety_margin_seconds`;
- the declared vector must fit configured node capacity;
- `[drain_at, end_at)` must not overlap another non-ended reservation's
  `[drain_at, end_at)` interval.

New reservation:

```http
201 Created
```

Idempotent replay of the same normalized, non-terminal reservation:

```http
200 OK
```

A new reservation and an immediate replay return:

```json
{
  "status": "SCHEDULED",
  "reservation_id": "night-heavy-20260813",
  "drain_at": "2026-08-13T22:58:00+09:00",
  "lease_deadline": "2026-08-13T22:59:55+09:00",
  "start_at": "2026-08-13T23:00:00+09:00",
  "end_at": "2026-08-14T01:00:00+09:00"
}
```

The `status` field always reflects the phase at response time, so a later replay
may return `DRAINING` or `ACTIVE` rather than `SCHEDULED`.

The reservation and its identifier record are persisted atomically. Reusing
the identifier with different normalized data returns
`409 RESERVATION_ID_REUSED`. Replaying an ended reservation returns
`410 RESERVATION_ENDED`; replaying a cancelled or early-released reservation
returns `410 RESERVATION_CANCELLED`.

### 7.3 Read a reservation

```http
GET /v1/reservations/{reservation_id}
```

```http
200 OK
```

```json
{
  "reservation_id": "night-heavy-20260813",
  "client_id": "scheduled-worker",
  "mode": "EXCLUSIVE",
  "resources": {
    "memory_mb": 7000,
    "gpu": true,
    "cpu_cores": 4.0
  },
  "status": "DRAINING",
  "drain_at": "2026-08-13T22:58:00+09:00",
  "lease_deadline": "2026-08-13T22:59:55+09:00",
  "start_at": "2026-08-13T23:00:00+09:00",
  "end_at": "2026-08-14T01:00:00+09:00"
}
```

Other responses:

- unknown reservation: `404 RESERVATION_NOT_FOUND`;
- ended reservation: `410 RESERVATION_ENDED`;
- cancelled or early-released reservation: `410 RESERVATION_CANCELLED`.

### 7.4 Cancel or release a reservation

```http
DELETE /v1/reservations/{reservation_id}
```

```http
204 No Content
```

Deletion is idempotent. Before `start_at`, it cancels the reservation. During an
ACTIVE window, it is an explicit early release of the entitlement and may allow
new leases immediately. The client must stop the scheduled workload before
deleting an ACTIVE reservation.

The Router also returns `204` for an already cancelled, released, ended, or
unknown reservation ID.

Deletion retains a terminal reservation-ID tombstone, so the same identifier
cannot later create another reservation.

The Router does not stop the workload and cannot make an unsafe early deletion
safe on the client's behalf.

### 7.5 Drain and renewal behavior

At `drain_at`, the Router:

- enters `DRAINING`;
- rejects every new lease request with `EXCLUSIVE_RESERVATION`;
- allows existing leases to release or expire naturally;
- never kills a workload;
- caps renewals so that `expires_at <= lease_deadline`.

The invariant

```text
drain_before_seconds
>= max_lease_ttl_seconds + reservation_safety_margin_seconds
```

applies to every lease mode, not only SHARED leases. It ensures that a lease
granted before `drain_at` can expire safely before reservation activation.

## 8. Router state

The public Router state is one of:

```text
RECOVERING
OPEN
DRAINING
EXCLUSIVE
```

| State | Meaning |
|---|---|
| `RECOVERING` | Persisted state is loading or has not yet been safely reconciled |
| `OPEN` | No node-wide exclusive owner or reservation drain blocks admission |
| `DRAINING` | An accepted reservation is waiting for `start_at`, lease clearance, and safe activation conditions |
| `EXCLUSIVE` | An immediate EXCLUSIVE lease or ACTIVE reservation owns the node |

Only these successful events may move the Router into a restrictive state:

- atomically granting an immediate EXCLUSIVE lease;
- reaching `drain_at` for a persisted EXCLUSIVE reservation;
- safely activating that reservation at or after `start_at`.

A BUSY acquire response never changes Router state.

`null`.

Null is different from a measured zero.

Status is informational only. It never creates entitlement, and clients must
not infer that a future acquire will succeed from this response.

## 11. Persistence, concurrency, and recovery guarantees

The implementation must persist at least:

- active and terminal lease records;
- successful acquire request records and request-ID tombstones;
- reservations and reservation-ID records.

Terminal records include a `terminal_at` timestamp. Permanent tombstone
retention is an accepted v1 operational limitation; automatic retention and
garbage collection are deferred and must not silently weaken idempotency.

The initial implementation uses one local-filesystem SQLite database in WAL
mode with `synchronous=FULL`. A grant, renewal, release, expiry, reservation
creation, or reservation lifecycle transition is reflected in memory only after
its authoritative transaction commits. A storage failure returns
`503 STORAGE_UNAVAILABLE`; it never returns BUSY.

Only active leases and non-terminal reservations form the resident working set.
Successful request records and terminal tombstones are looked up from SQLite
and are not retained in an unbounded in-memory collection. No database record
count, including 10,000 records, changes Router state or triggers BUSY.
Archiving terminal detail records while retaining compact authoritative
tombstones is deferred.

There are no pending-exclusive records in v1.

Lease acquisition and idempotency lookup occur in one atomic critical section.
Two concurrent claims must not consume the same capacity, and two concurrent
requests with the same `request_id` must not create two leases.

On startup, the Router enters RECOVERING, loads unexpired leases and
reservations, expires records whose deadlines passed, reconciles reservation
phase from persisted timestamps, obtains fresh telemetry, and only then becomes
ready. Restart never implies that all capacity is free.

The initial deployment uses one Uvicorn worker because the admission lock is
process-local. Multi-process coordination is outside v1.

## 12. Explicit v1 non-goals

The v1 API does not provide:

- `PENDING` acquisition or acquisition-status polling;
- immediate EXCLUSIVE drain intent;
- queue ownership, fairness, priority, or starvation prevention;
- `available_after` predictions;
- partial resource grants;
- SHARED reservations;
- workload preemption or termination;
- OS-level resource enforcement;
- Docker control;
- model routing;
- multi-node or distributed leases;
- fractional GPU quotas.

Immediate EXCLUSIVE starvation is an accepted v1 trade-off. A future version may
add an explicit drain-intent resource if operational evidence demonstrates that
it is required.
